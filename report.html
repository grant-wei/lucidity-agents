Lucidity. ML workflows in minutes, that you can follow.

Give it a CSV and a column to predict. Lucidity plans the work, runs AI agents on several kinds of model at once, and shows every step in plain English: what ran, what scored, what won, and why. Every score comes from rows the agents never saw, so what you read is real.

Live demo  grantwei.com/lucidity. The real app's screens replaying recorded runs. No key needed.
Author  Grant Wei, MGT 409, Fall 2026

1. Motivation

Answering "can we predict this column?" well is a whole workflow, not one step. You split the data so you have honest test rows. You set a baseline, so you know what "good" means. You try several kinds of model, from plain regression to boosted trees, and tune each one. You score them all on the same test rows, pick one, and explain why. A data scientist does this in an afternoon. Most people who have the question, like a manager, an analyst or a student in this course, can't do it at all.

AI coding agents changed half of that. Ask Claude Code, Codex or a notebook assistant to "predict churn from this CSV" and it will write a model. But what comes back is hard to follow. It's a long scroll of code and logs, usually one kind of model, and a score the agent reported about its own work. If you can't read the code, you can't tell what was tried, why it won, or whether the number is real.

So the gap isn't building one model. It's running the whole workflow, fast, in a form a non-expert can follow and trust. That's what Lucidity does.

  • Orchestrated. One upload turns into a full plan. Up to ten kinds of model get their own agent, run in parallel, and the best is merged. You make one choice, which models to try.
  • Fast. The traced run in section 3 compared nine kinds of model in 2 minutes 37 seconds for 3 cents.
  • Easy to understand. A plan you approve, a live race chart, a leaderboard, one plain sentence for every round of work, and a headline that says what won and against what.
  • Honest. The agents never see the test rows. Lucidity scores every attempt itself against the best answer you'd get with no agents, so the leaderboard can be taken at face value.

The gap. Agent tools build a model but leave you reading code. AutoML tools are fast but don't explain themselves. Enterprise platforms do both at an enterprise price. Lucidity runs the whole workflow with agents and shows it in a form anyone can follow. Three parts of that are new as far as I could find.

  • A race of model families, picked by a person. The planner proposes up to ten kinds of model from simple to complex. The owner ticks which ones to try, and each gets its own agent in its own git worktree, all running at once.
  • The workflow is the interface. The screen follows the steps as they happen. You see the plan, then agents working in parallel, then every score landing on a chart, then the best one kept, with a sentence for each round and a headline at the end.
  • Scores you can trust without reading code. The scorer refuses test scores to anything running as an agent, and any agent that edits the scorer or data fails before it's scored. The goal is to beat the best no-agent answer, like plain regression on every column, by at least 0.2%. Section 6 shows why that matters.

What existed before the course

Lucidity started before this course as a personal tool for watching my own coding agents: which ones were waiting on me, which were burning money, and whether "done" was really done. For the course I rebuilt it in a clean repo as an orchestrator for ML work, keeping the part that mattered most, which was making many agents' work easy to follow at a glance. Everything in the repo is new for the course. That includes the CSV setup and the locked split, the benchmark goal, the planner and family picker, the parallel agents in worktrees, the referee and checker, the race chart and leaderboard, the safety layer, the replayable demos, and the hosted demo.

3. The agents

Most of Lucidity is plain code on purpose. Splitting the data, computing the benchmark, running the scorer and deciding what merges are all things a program can do exactly. The model is only asked to do what a program can't: plan the work, write the model code, and explain what changed.

Grey boxes are plain code. Blue boxes are model calls on gpt-6-luna. The yellow box is the one human decision. Agents see the train and tune rows only. The referee is the only part that sees test scores.

Model choice. Every model call uses gpt-6-luna, the course model. The agents' work is small, like reading a 30-line file, writing a scikit-learn pipeline and reading a score. A bigger model doesn't buy much here. Section 4 shows the same table on Claude Haiku cost 96 times more and scored the same.

One real run, step by step

This is run 1017-134852-3650, recorded for this report on Oct 17, 2026, on the public Wisconsin breast-cancer table that ships in examples/. The table has 569 rows and 30 numeric measurements. The task is to predict whether a tumor is malignant. I uploaded it through the app and picked diagnosis as the column to predict.

1
Setup (code, $0). Split the rows 315 train, 137 tune, 117 test. Wrote a deliberately weak starting model, logistic regression on 2 of the 30 columns, which scores 0.2721 log loss on the test rows. Computed the benchmark, plain logistic regression on all 30 columns, at 0.2362. So the goal is 0.2357 or lower, without accuracy dropping.
2
Planner (1 call, 2,442 tokens, $0.0004). Wrote two tasks: build and compare model families, then integrate and verify the winner. It proposed nine families and flagged plain logistic regression on all columns as the expected best.
3
The owner's call. The run stopped and asked which families to try. I left all nine ticked.
4
Nine agents (140 requests, 677,178 tokens, $0.0216). Each worked on its own copy of the code. Most needed only one round. Naive Bayes and the single decision tree each took three, because their first tries fell short and were sent back.
5
Referee and checker (code plus 8 checker calls, $0.0020). Scored every round on the 117 test rows. None of the agents touched the scorer or the data. Eight of nine families beat the goal. The single decision tree didn't (0.3092), and k-nearest neighbors passed but within noise of the benchmark.
6
Merge. The best passing attempt merged at 0.0817 log loss, with accuracy up from 91.5% to 99.1%. The whole change was two files. features.py now uses all 30 measurements instead of 2. model.py standardizes them before a lightly penalized logistic regression.
-    return LogisticRegression(max_iter=1000)
+    return make_pipeline(StandardScaler(), LogisticRegression(C=1.0, penalty="l2", solver="lbfgs", max_iter=3000))

What the run teaches. The winner is the simple model. Ridge tied it exactly at 0.0817. That's expected, since scikit-learn's default logistic regression already carries the same L2 penalty, so the two agents wrote the same model. SVM came third at 0.0836, and the flexible models (random forest 0.1173, boosted trees 0.1269) did worse on a table this small. An agent working alone would likely have reached for boosted trees. The race shows on the user's own data that it shouldn't.

I've made 17 finished live runs on tables with gpt-6-luna, from Oct 14 to 17. They cover NBA games, Fed rate hikes, credit-card default, breast cancer, diabetes, Seattle weather and wine. Cost cuts, and whether they hurt

  • Pick the small model. On Oct 15 I ran the 30,000-row credit-card table with Claude Haiku as the worker. It cost $1.28 and scored 0.4276 log loss. On Oct 17 the same table, same split, with gpt-6-luna cost $0.0134 and scored 0.4281. A second run cost $0.0411 and scored 0.4270. So it's 96 times cheaper, with the score the same to within 0.001. Part of the gap is that the Haiku run used no prompt caching at all (0% of input cached).
  • Prompt caching. Stable instructions go first in every prompt, so the provider caches them. Across the 17 runs, the bill was $0.42. The same token counts priced with no caching would be $1.58, a 73% cut. Caching changes the price, not the answer, so it can't hurt accuracy.
  • Plain code before the model. The split, benchmark, scoring, tamper check and merge decision cost nothing in tokens. The model only writes code and summaries.
  • Stop early. Each agent gets at most 4 rounds and stops as soon as it clears the goal. In the traced run 7 of 9 agents stopped after one round.

6. Impact

Faster, and easy to follow

Before Lucidity, comparing several model families on a new table meant writing the split myself, a pipeline for each family, a loop to tune each one, and a scoring step I had to be careful never to peek at. Then I'd write up which one won and why.

It caught models that looked better but weren't

The strongest evidence came from a mistake in my own first version. Its goal was "10% better than the starting model." On Oct 15 the agents cleared that goal on two public tables. When I added the no-agent benchmark, both winners turned out to lose to plain textbook regression on the same test rows.

An agent grading itself against its own starting point would have reported a 29% and an 11% improvement and shipped both. Under the current rule both are misses, and the run says so. The Fed demo shows the same thing from the other side. The tuned models looked better on the tuning years and worse on the test years, so plain logistic regression won.

Who it's for

The clearest user is someone in my seat in this course. A manager or analyst who has a table and a question, and wants a real answer in minutes without writing a pipeline or reading one. Lucidity gives them the whole workflow as something they can watch and explain to someone else. That covers what was tried, what won, by how much, and whether it beat the simple answer. For an ML engineer it's a fast first pass at "which kind of model fits this table" that costs a few cents.

7. Limits and next steps

Limits

  • Small tables, one test split. Test sets of 100 to 6,000 rows give a noisy score. The app shows a standard error and calls near-ties near-ties, but one split isn't cross-validation.
  • The split can still leak. Lucidity hides the test rows, but a random split on data with repeated customers or time order can still flatter a model. Splitting by date or by group is available, and the user has to choose it.
  • The benchmark is only as good as its list. Plain regression, guessing and a coin flip are honest floors. A team's real current model would be a better bar, and it's only supported as an outside forecast column.
  • Agents mostly win by the obvious moves. On these tables the gains came from using every column and scaling them. Real feature work, like joins and domain features, is beyond what the agents attempted.
  • Local first. Live runs need Python, git and an API key on your own machine. The hosted demo replays recorded runs.

Next steps

  • Cross-validation on the train and tune rows, so a near-tie can be broken by more than one split.
  • Let a team upload their current production model's predictions as the benchmark to beat.
  • Run live on the hosted site. The server setup (a locked-down container with the key handed over in a file) is in the repo, not yet deployed.
  • Add AutoGluon as a family an agent can try, so the race includes the strongest fixed recipe.
