Lucidity

One screen for every coding agent you have running. It tells you which ones are waiting on you, which ones are burning money, and whether the ones that say "done" really are.

Repo  github.com/grant-wei/lucidity-agents
Live link  none. It runs on your own machine, because it reads the agent logs on your disk. Sample mode works with no agents of your own.
Author  Grant Wei, MGT 409, Fall 2026

1. Motivation

More and more people now work with several coding agents at once. A developer (or an SOM student, since this course teaches vibe coding) starts a Claude Code session to fix a bug, a Codex session to write tests, and a third to draft a README. Each runs in its own terminal tab. Then three things go wrong, over and over.

  • You don't see who's waiting on you. An agent stops to ask "may I run this command?" and sits there. Nothing tells you. You find out when you happen to click on that tab.
  • You find out about runaway spend too late. An agent stuck in a loop keeps calling the model. You learn about it from the bill or from hitting your usage limit.
  • "Done" isn't always done. Agents say "all tests pass" when they don't. You take the claim at its word, or you check every one by hand.

Today people deal with this by flipping through terminal tabs, by checking a usage page now and then, and by rereading the agent's work themselves. That costs attention all day, and it costs money when a loop runs unnoticed.

My own numbers, before this project. I run several Claude Code sessions plus Codex most days. The personal version of Lucidity priced my transcripts at list rates and found $6,445 of usage (13.2 billion tokens) over the 14 days to Oct 8, 2026. I pay a subscription, so that's the size of the usage, not what I was billed. Two incidents made the problem concrete.

  • An autoresearch loop I started ran for 37 hours with no defined end and used about $385 of list-price usage. Nothing told me it was still going.
  • From Oct 5 to 8, one of my own background jobs kept re-summarizing every tracked process on a timer, about 113,000 model calls (around 1,750 an hour). It was about half of my Claude tokens on Oct 8. I found it only by looking at a token chart.

These figures come from the personal Lucidity tool's logs on my machine, not from this repo.

2. What is new

There are good tools near this space, and I checked each one before writing this. They fall into three groups. None of them does the job Lucidity does, which is to supervise the coding agents you're already running, from their own logs, and tell you where your attention and money should go.

LangSmithTraces each step of an LLM app (model calls, tool calls, latency, cost), with dashboards, alerts, datasets and evals.You add its SDK to code you wrote. It doesn't look at the Claude Code or Codex sessions running in your terminals.

The twist. The runners are better than Lucidity at launching work and reviewing diffs. The tracing tools are better at instrumenting an app you wrote. Lucidity's job sits between them. It reads Claude Code and Codex logs together, needs no SDK or proxy, and answers three questions at once. Who needs me? What's wasting money, and why? Did the thing that says "done" actually pass? The third one is the newest. The done checker runs the task's own tests and grades the agent against a written contract, and the planner writes those contracts up front. I didn't find that pairing in any of the tools above.

What existed before this course, and what's new

Lucidity started as my personal tool, before this course started. That version is Windows-only, reads my own machine, calls Claude through headless claude -p, and is full of my other projects. None of it is in this repo. For the course I rebuilt it from a clean start. What carried over is the idea, my knowledge of the two log formats, the "skip what hasn't changed" fix, and the shape of the checker's verdict. Built new for this project:

  • The agent layer on gpt-6-luna through pydantic-ai (triage, watchdog explainer, done checker, planner), with typed outputs and a rule that every claim cites a log event.
  • Cross-platform log readers with no Windows APIs, so it runs on a Mac.
  • Sample mode, with 8 synthetic sessions and small test repos, so anyone can try it without agents of their own.
  • The safety layer (secret redaction, transcript-as-data prompts, a command allowlist, a spending circuit breaker) and its tests.
  • The "How it decided" flow view, the 30-case eval set with an Evals tab, and the recorded planner replay.
  • A usage log of every model call Lucidity itself makes.

3. The agents

Most of Lucidity is plain code on purpose. A program can tell, with certainty, that a tool call has been waiting for approval for 33 minutes or that the same command ran 321 times. The model is only asked the questions a program can't answer, like what an agent is doing and why it's stuck. When a plain-code fact and the model disagree, the fact wins.

Grey boxes are plain code. Blue-outlined boxes are model calls on gpt-6-luna. The planner writes the contracts the done checker later enforces (dashed line).

AgentModel?ToolsJob
Collectornoreads ~/.claude/projects and ~/.codex/sessionsParses each session, counts tokens and dollars, computes facts like minutes waiting and repeated calls.
Coordinatornochange signature per sessionSkips any session that hasn't changed since the last refresh and batches the rest, up to 10 per triage call.
Triage agentyessession_tail, session_stats, pending_questionsNeeds you, working or finished, plus what it's doing and has done. Every claim must cite event ids. Claims that cite nothing real are dropped.
Watchdog detectorsnothresholds in watchdog.pyFlags a session if the same call repeats 20 times, calls run at 3 a minute for 10 minutes, it passes $5, or the same failure repeats 4 times.
Watchdog explaineryessession_tailOnly for newly flagged sessions. Says why, and suggests pause, stop or let it run. It never stops anything. You click.
Done checkeryesread_done_when, git_diff, run_allowlistedFor a session that claims done and has a task contract. A program runs the tests, and the model grades each done-when line against the evidence.
Planneryesnone (plain code validates its output)Turns a goal into 2 to 6 tasks, each with done-when conditions, a budget and a cap on retry rounds.

Model choice. Every model call uses gpt-6-luna, the course model. It's also the right size for the job. Triage is classification plus two short sentences, and the eval set below shows it gets 29 of 30 cases right in the default setup. At $0.10 per million input tokens, $0.01 cached and $0.50 output, a full refresh of 8 sessions costs a fraction of a cent. A bigger model would make Lucidity cost more than some of the agents it's watching, which is the exact problem it exists to catch.

This is refresh 20261012T150353-be0f, a cold refresh of the 8 sample sessions with the done checker on. It took 37.8 seconds, 19,193 tokens and $0.0023.

On habit-tracker it ran python -m pytest -q, saw 2 failures, and found the new test was an empty placeholder, so it returned not verified. The planner, as a recorded replay

Sample mode never starts agents on your machine, so the planner is shown as a replay of a real run recorded on Oct 12. The goal was "add a dark mode toggle to a small flask app" with a $0.50 budget. The planner wrote 3 tasks, each with done-when conditions. A small worker did them, and the checker gated each one. The whole run took 41.2 seconds and $0.0021. It also caught something. Task 3's only condition ("the test suite passes") was already true before the worker started, so plain code marked it a weak contract, since passing it proves nothing.

Cost cuts, and whether they hurt

I built a labeled set of 30 cases (the 8 sample sessions plus 22 variants, for example a padded log, a second injection, or a session where the owner already answered) and ran each configuration 3 times from cold. Ranges are the worst and best of the 3 runs.

ConfigurationState rightInjections noticedRequestsTokensCostRepeat-refresh requests
Default. Batches of 10, last 14 events, skip unchanged. Also runs the checker on the 6 contract cases (5 to 6 of 6 verdicts right).29/308/821 to 2240,022$0.00500
Trimmed tail, last 6 events27 to 29/308/84 to 520,209$0.00270

From evals/results.json. Flags and secrets were right 30/30 in every configuration, and no configuration dropped a claim. The default row costs more because it includes the checker runs. Its triage-only cold cost matches the "no change skip" row, which is the same setup without the skip.

  • Skip unchanged sessions. The biggest cut over time. With it, refreshing when nothing has changed costs 0 requests. Without it, every refresh re-sends everything (5 to 6 requests each time on this set). On a real machine that refreshes every minute, that's the difference between my 1,750 calls an hour and almost none. No accuracy cost, since unchanged sessions keep their last answer.
  • Batch sessions into one call. One call per session used 2.5 times the tokens and 3 times the cost of the batched setup (68,153 vs 27,708 tokens, $0.0077 vs $0.0026) for at most one more correct case.
  • Trim the transcript tail. Cutting from 14 events to 6 saved about a quarter of the tokens but dropped accuracy to as low as 27/30. Going up to 30 events cost more and noticed one fewer injection in one run. So 14 stays the default. This is the one cut that did hurt when pushed too far.
  • Stable instructions first. The system prompt comes before any session text, so OpenAI's prompt cache picks it up. In the cold runs above, 4,199 input tokens were billed at the cached rate.
  • Rules before the model. The watchdog's detectors are plain code. The model only explains sessions they flag, and only the first time.

Lucidity reads logs that contain everything an agent saw, including web pages written by strangers and secrets printed by mistake. That shapes the risks.

7. Limits and next steps

Limits

  • It reads, it can't reply. Lucidity tells you a session needs you but can't answer it for you. Claude Code and Codex don't offer a supported way to type into a running terminal session from outside, and I don't want a tool guessing which window has focus.
  • Sample data is synthetic. The 30-case eval set is built from 8 made-up sessions and variants of them. Real logs are messier. The pilot is the real test.
  • Where it still gets things wrong. The most common miss across eval runs was a session where the owner had already answered the question and Lucidity still said needs you. A padded runaway was sometimes called needs you instead of working. The checker once called a real "done" not verified (5 to 6 of 6 right).
  • Contracts are only as good as their author. The checker can only verify what a done-when line says. The weak-contract warning catches conditions that were already true, but not every vague one.
  • Local only. It runs on the machine where the agents run. A team view would need logs shipped somewhere, which raises the privacy questions this version avoids.
  • Two agent tools. It reads Claude Code and Codex. Cursor, Gemini CLI and others write different logs.

Next steps

  • Run the pilot and replace every marker above with measured numbers and real quotes.
  • Measure time-to-notice for a waiting session, with and without Lucidity open.
  • In local mode, let the planner hand tasks to the user's own Claude Code or Codex, with the checker gating each one before it merges.
  • Grow the eval set with real, redacted sessions from pilot users and fix the "already answered" miss.
  • Add readers for more agent tools.
